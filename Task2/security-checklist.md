# Проверочный лист безопасности бизнес-систем PropDevelopment

## 1. Бизнес-системы

| Система | Данные | Что важно для безопасности |
|---------|--------|----------------------------|
| Витрина продаж, client-tour-app, client-mart-app | Контакты и паспортные данные клиентов, бронирования, сделки | Доступны из интернета. Несколько точек регистрации клиента. Интеграция с госорганами |
| client-crm-app, CRM собственников | Персональные данные клиентов и собственников | Основные хранилища персональных данных |
| auth-service-1 (Keycloak), Active Directory | Учётные записи | Клиенты жалуются, что видят в личном кабинете чужие данные |
| Мобильное приложение, tenant-core-app | Платежи ЖКУ, «Умный дом» | Можно управлять замком квартиры. Работает с API управляющих компаний |
| accountant-service-1 | Бухгалтерия, платежи | Финансовые данные |
| Хранилище (Greenplum, DWH на S3), BI | Копии данных всех систем | Нет ограничений на доступ к данным |
| Инфраструктура | Все данные | Firewall, собственный ЦОД и облако, резервные копии |

## 2. Выбор разделов

Взяты разделы I–IV шаблона из урока, потому что они закрывают проблемы компании. Из них оставлены только вопросы, которые относятся к этим проблемам.

- **I. Управление доступом.** Клиенты видят чужие данные, а у систем обработки данных нет ограничений доступа.
- **II. Безопасность данных.** Компания обрабатывает много персональных данных и не контролирует их потоки. Это мешает развивать BI/ML и грозит утечкой, как у конкурента.
- **III. Защита инфраструктуры.** Системы доступны из интернета и частично работают в облаке.
- **IV. Управление инцидентами.** Нужно вовремя замечать утечки. Специалист по ИБ один, и ему передают не все изменения.
- **V. Безопасность API партнёров** (свой раздел). Это отдельная проблема из кейса: партнёры видят чужие данные, а контракты API содержат персональные данные.

Раздел V шаблона «Специфические аспекты» (устройства и физическая безопасность) не включён: по этим темам в кейсе нет ни проблем, ни данных.

## 3. Проверочный лист

Пустая ячейка в колонке «Да/нет» означает, что в описании кейса недостаточно данных для ответа.

| №   | Вопрос | Да/нет | Комментарий |
| --- | ------ | ------ | ----------- |
| **I. Управление доступом** | | | |
| 1   | Используется ли многофакторная аутентификация (MFA) для доступа к критическим системам и сервисам? | | Нужна для управления замком и онлайн-сделки |
| 2   | Реализован ли принцип минимальных привилегий при назначении ролей и прав доступа? | Нет | У систем обработки данных нет ограничений на доступ |
| 3   | Автоматически ли удаляются или деактивируются учётные записи после увольнения или изменения должности сотрудников? | | Важно после смены руководителей IT-команд |
| 4   | Используются ли системы аутентификации пользователей для доступа к системам? | Да | Keycloak для клиентов, Active Directory для сотрудников |
| 5   | Ограничен ли доступ к системам из внешних источников? | Да | Через firewall, но API партнёров не защищены единой политикой |
| 6   | Ведётся ли единый реестр учётных записей? | Нет | Несколько точек регистрации клиента без координации |
| **II. Безопасность данных** | | | |
| 1   | Разработана ли политика классификации данных, и актуализируется ли она в соответствии с действующим законодательством? | Нет | Компания не уверена, что соответствует законам РФ |
| 2   | Используется ли шифрование на уровне базы данных, файловой системы и при передаче данных по сети? | | Проверить в первую очередь базы CRM и онлайн-сделки |
| 3   | Проводится ли регулярное резервное копирование данных? Хранятся ли резервные копии в защищённых хранилищах? | Да | Копии есть для всех БД. Как защищены хранилища копий, не известно |
| 4   | Ведётся ли учёт персональных данных, и применяются ли специальные процедуры обработки и хранения для различных типов данных? | Нет | Потоки данных контролируются не системно |
| 5   | Разработаны ли процессы и системы Data Governance для управления данными? | Нет | Проблемы с потоками данных блокируют BI/ML-сервисы |
| 6   | Применяются ли средства или процессы анонимизации данных? | Нет | Данные попадают в хранилище без обезличивания |
| **III. Защита инфраструктуры** | | | |
| 1   | Используется ли межсетевой экран для ограничения входящего и исходящего трафика? | Да | Внешние пользователи заходят через firewall |
| 2   | Реализована ли сегментация сети на логические зоны (DMZ, корпоративная сеть, гостевая сеть) для ограничения доступа к критическим ресурсам? | | |
| 3   | Проводятся ли автоматизированные сканирования облачных инфраструктур на соответствие рекомендациям безопасности? | | Облако используется для тестов |
| **IV. Управление инцидентами** | | | |
| 1   | Используется ли система мониторинга безопасности (SIEM) для корреляции событий и анализа аномалий в режиме реального времени? | | Одному специалисту по ИБ без неё трудно |
| 2   | Разработан ли план реагирования на инциденты, включающий анализ, эскалацию и восстановление системы? Проводится ли обучение сотрудников? | | |
| 3   | Как часто проводятся внутренние и внешние аудиты безопасности? Обновляются ли политики и процедуры на основе результатов этих аудитов? | Нет | Аудит проводится впервые, специалисту по ИБ передают не все изменения |
| **V. Безопасность API партнёров** | | | |
| 1   | Есть ли единая политика безопасности для API партнёров? | Нет | Прямо указано в кейсе |
| 2   | Ограничен ли доступ партнёра только к данным своей управляющей компании? | Нет | Партнёр видит и меняет данные другой УК |
| 3   | Проверяются ли контракты API на наличие лишних персональных данных? | Нет | Контракты содержат персональные данные |

## 4. Итоги

В первую очередь нужно исправить пункты с ответом «Нет»: разграничить доступ к данным, навести порядок в учёте и потоках персональных данных и ввести единую политику безопасности для API партнёров.
